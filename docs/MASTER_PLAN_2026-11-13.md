## 6. Capacity report for a 4 GB VPS

Measured locally (2026-11-13, production builds: Next.js standalone, API jar with `-Xmx448m`, PostgreSQL 17 container,
Keycloak 26 container; desktop with 16 logical cores — a 2-vCPU VPS is slower):

| Component | Idle | Under load (25 concurrent users) |
|---|---|---|
| Next.js standalone | 87 MB | **422 MB peak, ~0.9 CPU core** (the bottleneck: single-threaded server rendering) |
| Spring Boot API (`-Xmx448m`) | 224 MB | 255 MB, ~0.05 core (pages are cached by Next.js ISR) |
| PostgreSQL 17 | 82 MB | 86 MB |
| Keycloak 26 (staff sign-in) | **800 MB** | — |
| Throughput | — | 10 users: 46 req/s, p95 358 ms · 25 users: 53 req/s, p95 660 ms, 0 errors (mixed homepage, search, detail, projects, Hindi, API search) |

Not measured (needs the real server or services): ClamAV `clamd` (vendor guidance and common experience ≈ 1.2 GB with the
full signature set, roughly double during signature reloads unless concurrent reload is disabled), the notification
worker (runs inside the API JVM: + ~50–100 MB estimated), Caddy (~30–50 MB), image upload bursts (5 MB files held in
the API heap during scanning), Google/WhatsApp round-trips.

**Memory budget (MB):**

| | 4 GB VPS | 8 GB VPS |
|---|---|---|
| OS, Docker, Caddy, SSH, logs | 450 | 450 |
| PostgreSQL (shared_buffers 256–512 MB) | 400 | 900 |
| API + worker (`-Xmx512m` → ~750 RSS) | 750 | 1,000 (`-Xmx768m`) |
| Next.js | 450 | 600 |
| ClamAV clamd (`ConcurrentDatabaseReload no`) | 1,300 | 1,300 |
| Keycloak (if self-hosted) | 800 | 800 |
| **Total** | **4,150 — does not fit** | **5,050 — fits with ~2.9 GB headroom** |

Conclusion (honest): **a 4 GB VPS is not safe** if Keycloak and ClamAV both run on it. It fits only with (a) staff
sign-in moved off the box (e.g. a managed free-tier IdP such as Amazon Cognito — confirm its current free allowance) *and*
(b) a 1–2 GB swap file as a safety net, leaving ~500 MB headroom; signature reloads remain a risk. The traffic itself is
easily handled: a small real-estate site with 50,000 page views/day averages < 1 request/s; the measured ceiling is
~50 req/s on one core. Lightsail's burstable CPU could throttle long builds or scans — do not build images on the VPS
(build in CI and pull).

**Recommendation:** 8 GB. Within budget that means Hostinger KVM 2 (verify India location and terms) or, if AWS is
preferred, Lightsail 4 GB with Cognito + swap and a documented upgrade to 8 GB (₹4,880, over budget) when ClamAV memory
proves tight. **Single VPS = single point of failure**: no automatic failover; restore time = rebuild from scripts +
restore the latest backup (target RTO 4 h, RPO 24 h, or 1 h with WAL archiving later). Upgrade path: bigger VPS → move
PostgreSQL to a second VPS → managed database only when revenue justifies it.

## 7. Google login integration plan

Already built (verified in code): `GET /_bff/auth/google/start` (state, nonce, PKCE S256, `scope=openid email profile`,
`prompt=select_account`) → Google → `GET /_bff/auth/google/callback` (server-side code exchange with client secret +
verifier, nonce check) → API `POST /internal/v1/customer-auth/google` → `GoogleIdTokenVerifier` (Google JWKS RS256,
issuer `accounts.google.com`/`https://accounts.google.com`, audience = client id, expiry, `email_verified`) →
`customer_identities (provider, provider_subject)` unique → one customer per Google subject; session as an opaque token
in an HttpOnly cookie; no Google token reaches the browser. The redirect URI is
`${SITE_URL}/_bff/auth/google/callback` (`siteOrigin()` uses `SITE_URL`, then `NEXT_PUBLIC_SITE_URL`, then the request).

Exact Google Cloud Console values:
| Client | Authorised JavaScript origin | Authorised redirect URI |
|---|---|---|
| Development (separate project or client) | `http://localhost:3000` | `http://localhost:3000/_bff/auth/google/callback` |
| Staging (if used) | `https://staging.uainfrarealestate.com` *(proposed host)* | `https://staging.uainfrarealestate.com/_bff/auth/google/callback` |
| Production | `https://uainfrarealestate.com` | `https://uainfrarealestate.com/_bff/auth/google/callback` |

`www` is redirected to the root before sign-in, so it is not registered. Setup steps: company Google Cloud project →
OAuth consent screen (External; app name, logo, support email, privacy-policy URL `https://uainfrarealestate.com/en/privacy`,
authorised domain `uainfrarealestate.com`; scopes openid/email/profile only — non-sensitive, no Google verification
review expected) → "Web application" client per environment → secret into the server env only → set
`CUSTOMER_AUTH_MODE=google` (web) and `CUSTOMER_GOOGLE_MODE=google` (API). Testing mode first with named test users.
To add: last-login update check (exists in `CustomerAccountService`), an IT with a locally signed JWKS for the real
verifier path, and a staging test with a real Google account.

## 8. WhatsApp OTP integration plan

Today: Google first, then `POST /internal/v1/customer/whatsapp/otp` + `/verify` link a WhatsApp number to the signed-in
customer (`customers.whatsapp_e164`, `whatsapp_verified_at`; `phone_verifications` with `code_hash`, 10 min TTL, max 5
attempts, 30 s resend, 5 per hour per customer, superseded codes, audit `customer.whatsapp_otp_sent` / `phone_verified`,
codes never logged). Mock sender only.

Plan:
1. **Provider adapter** `MetaWhatsAppOtpSender` (Cloud API, authentication template with copy-code button, en/hi) behind
   the existing `WhatsAppOtpSender` port; mode switch stays `WHATSAPP_OTP_MODE`.
2. **Separate identities**: the CRM contact phone (`customers.phone_e164`, may be shared) stays separate from an
   **authentication phone identity** — new `customer_identities` row with `provider='whatsapp_phone'`,
   `provider_subject=<E.164>`, created only after OTP verification; the existing unique `(provider, provider_subject)`
   guarantees one account per auth phone. A number already linked to another account is refused with "sign in with
   Google" (no silent merge).
3. **Phone-OTP login** (future): `start` by number → if exactly one auth identity matches, send OTP → verify → session;
   otherwise require Google. Same limits plus **per-IP and per-number** limits (new), constant-time comparison, single use
   (`verified_at`), generic responses (no account enumeration), audit.
4. Webhook for delivery status (shared with notifications, §9). SMS fallback only after DLT registration and cost review.
